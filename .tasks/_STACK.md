# Stack profile — Python (uv)

Generated by `ai-tooling install`. **This file is the adapter layer**: everything that differs between
projects lives here as *data*. The core loop (`.claude/skills/`, `scripts/ai/`) never changes per project.

## Check kit

`scripts/ai/gate.sh` parses the block below. Keys with an empty value = "this project has no such step";
gates report them as `SKIPPED (not configured)` instead of inventing a command.

```ini
LINT_CMD=   # none: no linter configured in this repo (no ruff/flake8 in pyproject, no CI), see CLAUDE.md
TYPECHECK_CMD=uv run basedpyright src/linear_kit/
FORMAT_CMD=   # none: no formatter configured; do not introduce one as a side effect of a change
FORMAT_CHECK_CMD=   # none: see FORMAT_CMD
TEST_CMD=uv run pytest -q
TEST_ONE_CMD=uv run pytest -q <path>
BUILD_CMD=   # none: pure-python lib, hatchling only builds at publish time
RUN_CMD=uv run linear-kit
```

`FORMAT_CMD` writes (used by the on-edit hook); `FORMAT_CHECK_CMD` only verifies (used by gates).
`TEST_ONE_CMD` may contain `<path>` — gates substitute the target.

**An empty value needs a reason.** `LINT_CMD=` alone is indistinguishable from a forgotten one; write
`LINT_CMD=   # none: no linter in this toolchain, CI does not run one` and `doctor` reports the reason
instead of a warning. Everything after ` # ` is a note, not part of the command.

The reason changes the wording, not the verdict: an empty command is `SKIPPED` either way, and a gate
where **nothing** ran exits `3` (DEGRADED) rather than `0`. Declaring that this toolchain has no linter
is honest; it still means the run has no lint coverage to report.

## Repo facts

```ini
BASE_BRANCH=master
DEP_DIRS=.venv
LOCAL_ONLY_FILES=.linear-kit.toml
BOOTSTRAP_CMD=uv sync
SIBLING_REPOS=
DEFAULT_PROFILE=standard
TEST_PATHS=tests
SRC_PATHS=src
```

`DEP_DIRS` are symlinked into worktrees; `LOCAL_ONLY_FILES` are copied.

`BOOTSTRAP_CMD` runs inside a fresh worktree (and is what makes a fresh clone buildable): generated
artifacts — bindings, codegen, protobufs — must be **regenerated, never copied**. A copied artifact that
has drifted from its source produces a silently wrong build instead of an error.

`SIBLING_REPOS` lists other checkouts this product spans, as `<path>[:ro|:ask]`. A harness instance covers
one repository, so nothing in this repo's diff can reveal an edit made next door — `guard.sh siblings`
checks them for uncommitted changes instead. `:ro` means never touch it; `:ask` means the operator decides
before it is touched. `TEST_PATHS` / `SRC_PATHS` are what
`scripts/ai/guard.sh` uses to enforce phase file-scope (the builder may not touch tests, the test-author
may not touch src).

## Engines

```ini
IMPLEMENT_ENGINE=claude
ENGINES=claude:opus,claude:sonnet
```

`ENGINES` = the engines this project may actually use, comma-separated. **Being installed proves nothing** —
a CLI on PATH can be unauthenticated, unpaid, or rate-limited, and it will fail silently mid-review. Earn
the list instead of guessing it:

```bash
bash scripts/ai/engines.sh candidates      # what is on PATH
bash scripts/ai/engines.sh probe --write   # actually call each one, record the ones that answer
```

Entries may pin a model: `claude:opus`, `claude:sonnet`, `codex:gpt-5.5`. Different weights have different
blind spots, so when only one vendor is paid for, **model rotation is still real independence** — just
weaker than cross-vendor. The label is honest about which you got:

| Label | Meaning |
| --- | --- |
| `CROSS-ENGINE` | ≥2 vendors — strongest: different training, different failure modes |
| `CROSS-MODEL` | one vendor, ≥2 models — real but weaker |
| `DEGRADED` | one entry — the reviewer shares the implementer's blind spots; **not** an independent verdict |

Leave `ENGINES` empty → only `IMPLEMENT_ENGINE` is assumed usable and everything is labelled `DEGRADED`.
Under-claiming is deliberate: an unauthenticated CLI fails silently mid-review and a missing lens looks
exactly like a clean one.

## Per-worktree resources

Parallel worktrees share the machine. Anything single-instance must be allocated per worktree or
serialized. `scripts/ai/worktree-alloc.sh` writes `.tasks/_worktree.env` with a deterministic index and
port base; the project decides what to do with it.

```ini
PORT_BASE=4000
PORT_STRIDE=10
DB_SCHEMA_PREFIX=adw_
```

Resources that **cannot** be parallelized (one staging slot, one device, one editor instance, a paid API
budget) go in the list below. An implementer must ask the operator for these, never seize them.

- **Live Linear workspaces.** The only workspace and project an agent may touch is the one the local
  `.linear-kit.toml` binds to — `uv run linear-kit binding` prints it. Nothing else, ever: no other
  project in that workspace, no other workspace profile, no `-w/--workspace` override. Every other
  workspace is someone's real backlog, a mutation there succeeds silently, and reverting the branch does
  not undo it. (The binding file is gitignored on purpose — real workspace names stay out of the repo.)
- **Mutating `linear-kit` commands run `--dry-run` first.** The plan printed by a dry run is the same
  object the real run executes, so there is no reason to skip it. A live-API check the operator has not
  asked for is a seizure, not a verification.

## Grooming lenses

`groom-harden` rotates a lens per pass. These four are core. Add domain lenses here (they are data, not
code) — e.g. `economy`, `compliance`, `accessibility`, `multi-tenancy`.

```ini
LENSES=contracts,failure-modes,adversary,meta,linear-api
```

`linear-api` is this project's domain lens: every real bug here came from the API behaving unlike the
schema suggested (`workflowStateCreate` ignoring `position`, `viewPreferencesUpdate` replacing instead of
merging, `preferences` validated by nothing). The lens asks: is this shape *observed* or *guessed*, does
read-back actually prove anything here, and does the plan say who looks at the Linear UI to confirm?

## Review rubric lenses

`review-fanout` runs one reviewer per lens, plus a wildcard that hunts what these lenses cannot see by
construction. Add domain lenses the same way.

```ini
REVIEW_LENSES=correctness,linear-api,security,performance,architecture,tests
```

`linear-api` is listed second on purpose: the `standard` profile runs only the first three lenses, and on
this codebase an unobserved API assumption is a likelier defect than a performance one. Its rubric block
lives in `.claude/skills/slice-review/SKILL.md` (mirrored into `.codex/`) — a lens named here with no
`### lens:` block there gets the base rubric and no instructions, which reads as a clean lens. That block
is the one deliberate edit to a generated core file, so `install.sh doctor` reports both copies as `DRIFT`
and `install.sh install --force` overwrites them: after any harness upgrade, re-add the block and re-copy
`.claude/skills/slice-review/SKILL.md` over the `.codex/` one.

The `linear-api` reviewer checks the same thing at review time: names resolved during planning rather than
inside a `Step` closure, reconciliation still additive-only and idempotent, `preferences` overlaid onto the
stored object rather than replacing it, and no `Literal` vocabulary in `models.py` widened by guessing.

## Conventions

Every tool runs through `uv run` so it resolves against the locked environment, not whatever happens to be on PATH. Commit the lock file. Do not `pip install` into the venv by hand — add the dependency and re-lock, or the next `uv run` silently drops it.

`basedpyright` is the one exception: it is configured in `pyproject.toml` but is **not** a declared
dependency, so `uv run basedpyright` resolves it from a global install. On a machine without it the
typecheck gate fails with a spawn error rather than a type error — `uv tool install basedpyright` (or
`npm i -g basedpyright`) fixes that; do not add it to `[dependency-groups]` to make a gate green.

There is no linter and no formatter here, deliberately. Do not introduce one inside an unrelated change —
a repo-wide reformat buries the diff that was actually reviewed.

## Task intake

How tasks enter the loop. The core knows a **contract** (`id`, `title`, `body`, `url`, `status`) and runs
**your** command to satisfy it — it never knows the tracker. No MCP required; whatever you already use is
first-class. `<ref>` is replaced with the ticket key, `<value>` with the status or comment text.

```ini
INTAKE=linear
INTAKE_CMD=uv run linear-kit issue show <ref> --json
INTAKE_CWD=   # repo root: the binding is .linear-kit.toml, and LOCAL_ONLY_FILES copies it into worktrees
INTAKE_SKILL=linear-tasks
INTAKE_WRITEBACK=true
INTAKE_STATES_CMD=uv run linear-kit inspect states
INTAKE_STATUS_CMD=uv run linear-kit issue update <ref> --state <value>
INTAKE_COMMENT_CMD=uv run linear-kit issue comment <ref> --message <value>
```

Status names differ per team and per tracker ("In Progress", "Doing", "Начали"), so the loop moves tickets
by **intent**, not by name:

```bash
bash scripts/ai/intake.sh states SM-12                  # show how intents resolve here
bash scripts/ai/intake.sh writeback SM-12 --status start
```

`INTAKE_STATES_CMD` prints the tracker's workflow states as JSON; the core reads each state's `type`
(`started` / `completed` / …) and picks: `start` → the earliest in-progress state, `review` → the review
column, `done` → a completed state. A workspace-wide listing is narrowed to the ticket's own team using
the key prefix. Leave `INTAKE_STATES_CMD` empty and `--status "Some Name"` is passed through literally.

`INTAKE_CWD` is where intake commands run. Tracker CLIs commonly resolve their target by walking **up**
from the working directory, so the same command run from a worktree can bind to a different project — or
to none. A misdirected write lands in someone else's backlog and does not fail. Leave it empty to use the
repo root; set it when the binding lives outside the repository.

`bash scripts/ai/intake.sh fetch <ref>` runs `INTAKE_CMD`, maps common JSON field names to the contract,
and writes the body to `.tasks/<id>/extra_context/ticket.md`. Output it cannot map → it hands the raw text
to the agent, which normalizes it using `INTAKE_SKILL`. Empty `INTAKE_CMD` → manual intake: the operator
pastes the ticket. **Never invent a ticket** because a fetch failed.

**This block is the only statement of which tracker this project uses.** Empty `INTAKE_CMD` means manual
intake — it does **not** mean "figure out which tracker CLI is installed". A tracker tool being present on
the machine, or used in another repo, says nothing about this one; filing a ticket into the wrong
workspace succeeds silently and nobody notices until someone reads the wrong backlog. Configuration
examples for common trackers live in the `task-intake` skill, deliberately not here.

`INTAKE_WRITEBACK=false` by default: agents read the tracker freely and write almost never. Set it to
`true` and the loop makes exactly two writes — move the ticket at the start, and post the PR link at the
end. Closing the ticket stays a human decision, like merging.
